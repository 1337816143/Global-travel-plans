# 全球旅行攻略与可组合行程规划器

## 1. 产品定位

本项目不是“输入几个条件后返回若干景点”的轻量行程生成器，而是一个长期维护的旅行攻略与决策系统：

1. 先提供达到可独立使用标准的完整目的地攻略；
2. 再让用户从完整攻略中选择必去、想去、可选和排除项；
3. 由 Planner 将经过核验的日程模块、POI、交通、休息和约束组合成旅行周期内的逐日计划；
4. 用户能够拖动、拆分、合并、锁定、替换和重新规划；
5. 所有生成结果仍保留完整说明、Plan B、来源与信息边界。

`1337816143/travel-plans` 的青岛项目是首个内容与交互样板。Global 页面不能以少量 fixture 取代其信息密度。

## 2. 页面信息架构

### 2.1 全球首页

- 国家、城市、区域目录；
- 搜索、最近浏览、收藏和已创建旅行；
- 城市攻略完整度、最近复核日期和适合旅行天数；
- 明确区分“完整攻略”“建设中”“仅基础资料”。

### 2.2 城市攻略工作区

采用“左侧攻略与规划面板 + 右侧交互地图”的核心结构，并保留移动端适配。

标签页至少包括：

- 城市概览；
- 必去与候选点；
- 逐日计划；
- 日程模块；
- 预约与票务；
- 餐饮与必吃必买；
- 住宿分析；
- 交通；
- 旅行工具；
- 信息来源。

### 2.3 POI 详情

每个 POI 不是一张只有名称和坐标的卡片，而应显示：

- 为什么值得去；
- 推荐优先级和适合人群；
- 推荐停留时间和最佳时段；
- 入口、交通和步行强度；
- 开放、预约、票务和动态信息；
- 天气、体力、无障碍和安全边界；
- 避坑、替代点和 Plan B；
- 来源、复核时间与可信度。

## 3. 用户规划流程

1. 选择目的地、日期或旅行总天数；
2. 阅读完整攻略并筛选 POI；
3. 标记“一定要去 / 想去 / 可选 / 不去”；
4. 选择旅行强度、体力、预算、午休、每日时间窗、交通与住宿约束；
5. Planner 优先选取覆盖必去项的完整日程模块；
6. 不足或冲突时拆分半日模块并补充单点；
7. 自动插入真实或明确标为估算的交通、用餐、休息和入住事项；
8. 输出逐日时间轴、地图路线、住宿、预约、风险和 Plan B；
9. 用户拖动整日模块、半日模块或单点进行调整；
10. 锁定后重算，未锁定部分自动优化。

## 4. 日程模块

日程模块是攻略内容和 Planner 之间的桥梁。

模块类型：

- 抵达；
- 离开；
- 半日；
- 一日；
- 夜间；
- 休息；
- 机动补漏。

每个模块包含：

- 推荐适用旅行天数；
- 区域与 POI 集合；
- 完整时间块；
- 交通、用餐、休息和准备事项；
- 季节、星期、天气、开放和预约条件；
- 可拆分模块、可合并模块和冲突模块；
- Plan B 模块；
- 来源和采用理由。

## 5. 青岛迁移原则

青岛迁移必须以原项目最新数据为准，不允许：

- 只复制景点名称而丢弃长说明；
- 把原逐日时间轴压缩成上午/下午两个摘要；
- 删除 Plan B、住宿分析、预约、候选酒店、旅行工具或来源；
- 用算法重新生成未经核验的交通和开放时间覆盖原数据；
- 因迁移到 React 而降低页面信息密度。

原固定 8 日计划需转成可组合模块，同时保留一个“原版完整 8 日方案”预设供用户一键恢复。

## 6. 内容完整度门禁

一个城市只有满足以下条件才标记为“完整攻略”：

- 城市概览、住宿、交通、预约和来源齐全；
- 必去和主要推荐点均有富 POI 详情；
- 至少覆盖推荐最短、理想和最长天数的模块组合；
- 至少一个雨天/关闭/高温 Plan B；
- Planner 能覆盖全部 must-visit，并解释未采用内容；
- Schema、引用完整性、Planner、拖动编辑和 E2E 全部通过；
- 动态信息明确标识，不伪造实时值。

## 7. 非目标

- 不追求一次性批量生成数千个低质量城市简介；
- 不把未经核验的 AI 文本当成已发布攻略；
- 不以“能打开页面”作为城市完成标准；
- 不删除青岛 Legacy 或其回退路径。
